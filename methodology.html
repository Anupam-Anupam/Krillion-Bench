ENGINEERING NOTES / KRILLION BENCH

Building a benchmark
beneath the surface.

How we built a browser harness to compare language models on seven timed questions—and turn their actual gameplay into auditable results.

By Anupam Chettimada · November 10, 2026

← Back to the leaderboard

01 / THE TASK

Knowledge under a running clock

Krillion’s Daily Dive asks seven questions, each with a 25-second timer. Rarer accepted answers earn more points. Our question was practical: how well can a language model retrieve an unusual answer, express it concisely, and submit it through a browser before time runs out?

The measured system includes inference, structured output, browser actions, and the game’s feedback. A fast model can still lose time to rejected answers or invalid actions. A knowledgeable model can miss the submission deadline. The final score captures that combination.

The roster contains 100 exact model endpoints. Free and paid variants are separate entries. We preserve endpoint identity, saved pricing, execution settings, and source hashes in manifests so the configuration behind a result can be traced.

02 / THE HARNESS

A small observation-to-action loop

The harness is a standalone Python program. Browser Use Cloud supplies managed browser sessions; Playwright reads the rendered game and executes actions. Model adapters send the same game-playing instructions and action schema to the selected endpoint.

We extract the visible prompt, round label, timer, answer field, enabled controls, feedback, and scorecard. The model receives a compact observation with the current phase, allowed actions, and recent action results. Benchmark play uses DOM observations; optional screenshot support exists in the harness.

Read visible state→Ask the model→Validate actions→Act & observe again

The response schema permits one to three actions: click, fill, wait, or done. Buttons must match exact visible game controls. Fills target the enabled “Your answer” field. The shared prompt asks for at most five words per answer and permits batching a fill with the DIVE click.

{"actions": [
  {"kind": "fill", "target": "Your answer", "text": "…"},
  {"kind": "click", "target": "DIVE"}
]}

Before each action, the harness reads the page again. If the round or answering phase changed, it discards the remaining actions and observes again. This prevents a delayed response from entering an answer into the next question. The model plays from its own knowledge; the benchmark supplies no external search or answer bank.

03 / TIMING

The browser clock sets the deadline

The harness uses a monotonic clock independently of model calls. It timestamps each observation before the remote browser read, then derives a conservative deadline from the visible countdown. One second accounts for the integer display, and the configured three-second submission margin reserves time for browser and network overhead.

A later observation can shorten the current round’s deadline but cannot extend it. Model inference and browser actions share that remaining budget. When it expires, answering stops; the harness waits for the game’s real timeout and continues to the next round. It never converts a late answer into an action.

Krillion can propose a correction to a submitted answer. Our recorded correction policy confirms only the exact suggestion the site has placed in the textbox for that round’s latest submission. It rechecks the input, correction, and deadline, bounds correction chains, and records the original and canonical answers. This assistance is part of the protocol.

04 / VERIFICATION

Trust the scorecard, then check it

A completion signal alone is insufficient. Verification requires the visible DIVE COMPLETE state, the COPY RESULT control, seven observed rounds, and seven unique scorecard entries covering rounds one through seven. The sum of their points must equal the displayed final score.

Real zero scores count. Question timeouts, rejected answers, and malformed model responses are retained as outcomes. If the agent stops permanently, bounded navigation-only collection can let the remaining timers expire and reach the actual final scorecard. It never supplies replacement answers. A browser failure without a verifiable scorecard remains unresolved.

For archived puzzles, we first observe the calendar’s date, URL, and dive label. Each prepared browser must match that puzzle and show a clean start. A fingerprint of the seven visible prompts is checked across models on the same date. Daily sessions begin independently; archive access uses the dedicated authorized profile and the game’s replay controls.

05 / ORCHESTRATION

Keep completed games immutable

Campaign coordination uses a rolling worker pool: a slot becomes available after a game finishes and its report is durably stored. Paid work can use up to ten concurrent browser slots. The shared free endpoints run one game at a time with 3.1-second request pacing to respect their shared request limit.

Infrastructure failures pause new scheduling and drain active work. A clean verified model/date result is terminal, including a zero or a poor answer. Eligible infrastructure recovery requires an explicit authorization tied to the prior report’s checksum; replacement attempts retain their predecessor and provenance. We never choose the best score from repeated clean games.

Current campaign reports are compressed in memory and written to private cloud storage. Upload identity, checksum, and durable readback are checked before publication. Raw browser observations and trajectories remain private. The website receives numeric exports and sanitized Daily gameplay summaries.

06 / ACCOUNTING

Separate gameplay from billing capture

Usage is captured before action JSON is parsed, so an unusable model response can still retain its reported cost. Where the API supplies an account charge, we keep it. Otherwise, recorded tokens and frozen catalog prices provide a labeled estimate. Reasoning tokens already included in output usage are not added again.

The billing capture revision lets an in-flight HTTP accounting task finish after gameplay cancellation, with up to 60 seconds of collection after play. Missing usage or cost can be reconciled using only generation identifiers returned by that run. Those identifiers and authorization headers remain in memory and are excluded from public output.

That extra collection time cannot extend a question or submit a delayed answer. Unresolved requests remain unresolved. Earlier runs did not retain every identifier needed for reconciliation, so historical accounting can stay partial; we do not replay clean games to fill those gaps.

07 / PUBLISHING

Available data, explicit limits

Average scores are arithmetic means of available clean model/date results. Missing games are excluded rather than scored as zero, so coverage can differ between models. Each accounting metric uses its own available complete samples; partial totals do not enter complete-cost means. Daily reports can display recorded partial totals with a ≥ marker.

The graph compares average score with an available numeric metric. Daily lets readers inspect a tested date and its sanitized reports. An exact authorized publication registry limits which private reports the service can consider; verified additions refresh the public projection without exposing raw storage paths.

This measures timed Krillion performance. It combines knowledge, latency, answer choice, provider behavior, and browser interaction. It is not a general intelligence ranking, and the game’s “better than” percentile is a comparison captured from Krillion—not a percentile within our model roster.

08 / CHECKING OUR WORK

Test the boundaries of the measurement

Validation began with browser startup, scripted control runs, and model pilots. Control answers exercised the controls and verifier; they were confined to those diagnostics. Automated checks cover deadline behavior, action and correction guards, scorecard recovery, missing accounting, immutable storage, and aggregation.

Billing checks exercise cancelled requests, late numeric usage, generation reconciliation, and identifier exclusion. These checks support the mechanics of the harness. They do not establish provider uptime or eliminate variation across puzzles and endpoint routes. Source revisions and preserved history make those boundaries inspectable.
